# Phase 6: AC-Aware QA

This command runs the AC-Aware QA phase for the experimental delivery pipeline.

## Role Contract

Execute focused QA against the local implementation using the ACs and validation targets. Do not refactor or edit code. Produce expected vs actual results and fix requests when behavior fails.

## Shared Pipeline Rules

Read `commands/shared-preamble.md` if available. Enforce these critical rules even if it is unavailable: treat runner-provided paths as the only runtime authority, read previous artifacts as immutable inputs, write only this phase's listed artifacts, never invent evidence or QA results, never include secrets/tokens/auth headers/cookies in artifacts, and always write schema-valid `output.json` before ending.

This is a validator phase. Do not edit code, tests, data fixtures, package files, or git state. Behavior failures must become fix requests.

## Skill References

Use `manual-qa` for AC-aware QA structure. Use `playwright-mcp` when browser interaction, preview/local URL inspection, or auth-aware inspection is needed. Use analytics tooling such as `amplitude-analytics` only when the ACs or linked specs require checking persisted analytics data; otherwise verify browser-side tracking through observable console or network evidence.

## Inputs

Read:

- `state.json`
- `context-packet/`
- `implementation-plan/validation-plan.json`
- `current-diff/`
- prior verdicts under `verdicts/`
- local app instructions from the target repo when needed

## Required Work

1. Build a focused QA checklist from ACs and validation targets.
2. Run observable behavior checks locally when practical.
3. Include regression checks for changed files that are not directly explained by the ticket.
4. For each failure, record scenario, expected, actual, reproduction, environment, and related AC IDs.
5. If the app or route cannot be reached, try reasonable local/route/data/flag fallbacks before declaring blocked.
6. When the ticket involves tracking or analytics, trigger the relevant user actions and verify event names, properties, payload values, timing, and negative cases against the ACs or linked specs using console logs, network requests, or required analytics tooling. Do not pass tracking QA without payload evidence.
7. When the ticket involves A/B tests, experiments, feature flags, or variants, verify both control and treatment behavior when reachable. Identify the source-of-truth assignment path and supported override mechanism from code, docs, runtime state, or tooling; do not invent cookie or storage keys. After applying an override, reload and verify the active variant through rendered UI, exposure/tracking payload, network response, or runtime state. A stored override key alone is not proof.
8. Do not patch code. Send failures to the Implementer/Fixer as fix requests.

## Phase Checklist

- QA scenarios map to AC IDs and validation targets.
- Each run records environment, route/surface, data/flag setup, expected behavior, actual behavior, and reproduction steps.
- Tracking checks record event names, expected properties, observed payload evidence, and negative cases when tracking is in scope.
- Variant checks record control/treatment expectations, the confirmed override source, and proof that the active variant changed when A/B behavior is in scope.
- Local recovery attempts are recorded before declaring blocked.
- Failures produce fix requests; blockers state exactly what human input/access is needed.
- Passing verdict includes what was checked and any meaningful untested risk.

## Artifacts To Write

Write these files:

- `verdicts/06-qa.json`
- `phases/06-qa/output.json`
- optional `phases/06-qa/notes.md`
- optional fix request files under `fix-requests/`

Required artifact list: `["verdicts/06-qa.json","phases/06-qa/output.json"]`.

## Output Rules

The final file must be valid JSON at `phases/06-qa/output.json` using `schemas/phase-output.schema.json`.

Set `schema_version` to `"1"`. The `phase` field must match this command phase ID.

Use `status: "pass"` when relevant QA scenarios pass. Use `status: "fail"` for implementation behavior failures. Use `status: "blocked"` only after recovery attempts are recorded.

Do not edit files. Do not end without writing `output.json`.

Example `output.json` blocked shape:

```json
{
	"schema_version": "1",
	"phase": "qa",
	"status": "blocked",
	"summary": "The target route requires access that is not available locally after documented recovery attempts.",
	"inputs_read": ["context-packet/", "implementation-plan/validation-plan.json"],
	"artifacts_written": ["verdicts/06-qa.json"],
	"evidence": [{ "type": "qa-attempts", "description": "Recovery attempts are recorded in the verdict.", "path": "verdicts/06-qa.json" }],
	"fix_requests": [],
	"blockers": [{ "type": "needs-access", "message": "Local route requires a flag or credential that was not available.", "needed_from_human": "Provide the flag override or test account needed to reach the route." }],
	"stale_artifacts": [],
	"next_recommendation": "pause-for-human"
}
```
